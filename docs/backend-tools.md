# 可能需要後端的分析工具（提案）

> 2026-11-15，`ui/ux-refresh` 前端翻新時整理。目前 `/detective` 的統計全在瀏覽器內跑（`lib/detective/analysis.ts`、`intervalDetail.ts`），
> 資料是預先打包的子流域月平均（`web/public/data/series/<區域>.json`，34 個資料層）。
> 下面列出「瀏覽器做不到或做不好」的工具；最後一節列出看似要後端、其實前端就能做的項目，避免多開服務。

判斷是否需要後端的標準：需要 **大量或網格資料**、**金鑰／權杖**（Earthdata、LLM API）、**跨所有區域的預先計算**，或 **持久化狀態**。

## 一、建議做（依價值排序）

| # | 工具 | 使用者得到什麼 | 為什麼要後端 | 介面草案 | 工作量 |
| --- | --- | --- | --- | --- | --- |
| B1 | **AI 假說：方向＋理由** | 每個建議變數附「預期偏高／偏低」與一句理由，例如「乾旱 → 根區土壤水偏低」。工作台把它當假說，用 ✓／✗ 對照實際結果；目前只有預設事件有 `expected` | 呼叫 LLM（金鑰）；擴充現有 `/api/select-variables` 即可 | `SelectResponse.votes[]` 加 `expected?: "high"\|"low"`、`reason?: string`（**contract change**） | S |
| B2 | **事件 → 地點／時間解析** | 輸入「2022 巴基斯坦洪水」就自動選好子流域（可能多個）與月份；現在只靠正規表示式加國名表 | 地理編碼服務（GeoNames／Nominatim）或 LLM＋工具；需金鑰與速率限制 | `POST /api/resolve-event {event}` → `{time, regions: [{id, why}], confidence}` | M |
| B3 | **結果摘要（有護欄的 LLM 敘述）** | 一段 3 句的研究筆記：「土壤水在事件前 2 個月已低於 −2σ，降水同期不顯著……」，可複製進報告 | LLM 金鑰。輸入只給已算好的統計 JSON，不給原始資料；提示詞禁止因果用語，數字必須出自輸入 | `POST /api/summarize {query, lanes: IntervalDetail[], trend}` → `{text, citedFields[]}` | S |
| B4 | **全球同類事件比對（analog）** | 「這個區間在全球 1,313 個子流域裡排第幾」「過去哪些流域出現過類似的多變數異常組合」 | 要對所有區域×所有資料層預先算殘差與 z（約 1,313×34×500 個月），屬批次運算；結果可輸出成靜態索引，不一定要即時服務 | 管線 F 新增 `build_anomaly_index.py` → Release 附件；前端或小型 API 查詢 | M–L |
| B5 | **事件的空間異常圖** | 地球上直接看異常出現在子流域的哪一側、是否延伸到鄰近流域，不只看流域平均 | 需要網格資料（GB 級），不適合放進前端資料包；要做圖磚或依事件預先裁切 | `GET /api/anomaly-tiles/{layer}/{YYYY-MM}/{z}/{x}/{y}.png`，或依預設事件預先算好 | L |
| B6 | **自訂區域與上游集水區** | 使用者畫多邊形，或把「上游所有子流域」合併成一個區域（洪水常由上游降雨造成） | 需要網格資料做區域統計；可用 Harmony／Giovanni 的 area-average 即時取數（伺服器持有 Earthdata 權杖並做快取） | `POST /api/zonal {geometry \| regionIds[], layer}` → `MonthlySeries` | L |
| B7 | **近即時與日資料** | 剛發生的事件（資料包最晚到 2025-09～2026-10，因層而異）；短事件（洪水、熱浪）用日資料，不被月平均稀釋 | 要定期抓官方最新資料（排程）；日資料量太大，無法整包下載 | 排程任務更新 Release；日資料走 B6 的即時取數 | M |
| B8 | **報告匯出（PDF）** | 一鍵產出含圖、統計表、資料來源與 DOI 的 PDF，可附在報告或簡報 | 伺服器端無頭瀏覽器排版較穩；也可先用前端列印 CSS 過渡 | `GET /api/report.pdf?<detective URL 參數>` | M |

建議順序：**B1 → B3 → B2**。這三項都只是擴充現有 Next API route，不需要新的資料管線，而且直接回應「使用者知道事件、想知道哪些變數有關」的核心流程。B4 是評審最容易感受到「偵探」價值的功能，但要和管線 F 協調。

## 二、要討論再決定

| 工具 | 說明 | 疑慮 |
| --- | --- | --- |
| 變數間領先／落後的因果檢定（Granger、transfer entropy） | 「降水異常是否領先土壤水異常 2 個月」 | SPEC §7 明定本版不做跨變數關聯；月資料樣本短，容易過度解讀成因果。若要做，建議用 Python（statsmodels）實作並清楚標示「預測性，不是因果」 |
| 儲存與分享調查（筆記、標註） | 研究者存下多個區間與結論 | 需要帳號與資料庫；SPEC 不做帳號。目前用完整 URL 狀態分享已足夠 |

## 三、看起來要後端，其實前端就能做

| 工具 | 做法 |
| --- | --- |
| 掃描同一子流域全部 34 個資料層，依異常程度排序 | 一個子流域的所有層都在同一個 JSON 檔（已快取），在瀏覽器跑 `decompose`＋`intervalDetail` 即可；運算量是毫秒級 |
| 領先／落後掃描（選取區間往前後平移 ±12 個月，看哪個位移最顯著） | 純計算，前端可做；要附上多重比較警告 |
| 多重比較校正（同時看 n 個變數、多個區間） | Benjamini–Hochberg 在前端算；工作台可多顯示一欄 q 值 |
| 自助重抽樣（block bootstrap）／AR(1) 代理序列的 p 值 | 每個變數約 1,000 次重抽樣，放 Web Worker 就不會卡畫面 |
| 氣候指數當背景變數（Niño 3.4、IOD、SAM） | 資料量很小（全球一條月序列），由管線 F 加進資料包即可，不需即時服務；2019 澳洲黑色夏季就與正 IOD 有關 |
| CSV 匯出 | 已在前端實作（工作台統計面板） |
